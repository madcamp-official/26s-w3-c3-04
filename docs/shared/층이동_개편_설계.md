## 0. 목적

현재 층이동(하강·상승)은 **평상시와 예측이 서로 다른 방식**으로 동작하고, 이동 자체도
물리감이 없으며, 층 전환 지점을 **저작자가 통제할 수 없다**. 이를 전면 개편한다.

핵심 방향:
- **맵에 손으로 배치한 마커가 층이동의 유일한 권위.**
- 이동은 **정점이 보장된 탄도 운동**(확실히 솟았다 가속하며 떨어짐).
- 마커마다 **어떤 몹이 어느 방향으로 쓸 수 있는지**를 종류로 지정.
- **구조물을 뚫지 않음이 보장**되고, 저작자가 **눈으로 보며 튜닝**할 수 있다.
- 평상시 길찾기는 **NavMesh의 전역 최적 경로**를 그대로 살린다(퀄리티 최우선).

## 1. 현재 시스템 (사실 정리)

### 1.1 이중 길찾기 구조

`EnemyMovement.Step`이 `svc.Pathfinder.NextStep`을 부르는데, 그 구현이 상황에 따라 다르다.

| | 평상시 | 예측 · following |
|---|---|---|
| 구현 | `NavMeshPathfinder` | `GraphPathfinder` |
| 경로원 | Unity NavMesh(오프메시 링크 포함) | 손으로 짠 노드·링크 그래프 |
| 산출 MoveKind | **Walk / Drop 둘뿐** | Walk / Drop / JumpUp / Boost |
| 층 전환 판정 | **기하 자동판정** (낙차 > `DropDetectMinHeight` 이고 낙차 > 수평 × `DropDetectRatio`) | 링크의 `NavTraversalType` |
| **에이전트 게이팅** | **없음** (`agentMask` 인자를 무시) | `agentMask`로 몹별 제한 |
| `FloorIdAt` | `-1` (미지원) | 노드의 floorId |

예측이 그래프를 쓰는 이유: NavMesh는 **결정론적 포크·재현이 불가**하고
(예측 1회당 SimStep 호출 ≈ 337k), 계약 §8.3이 예측 루프 내 NavMesh 호출을 금지한다.

### 1.2 현재 traversal 실행 (`EnemyMovement.StepTraversal`)

발판(`traversalStart`)까지 걸어가 도착하면 `StartTraversal` → 3단계:

| 단계 | 틱 | 동작 |
|---|---|---|
| `Pause` | `TraversalPauseTicks` = 12 | 정지(주저) |
| `Airborne` | 기본 `TraversalDefaultAirTicks` = 30 | `Vector3.Lerp(start→end)` + `y += sin(t·π) × TraversalArcHeight(1.25)` |
| `Recovery` | `TraversalRecoveryTicks` = 15 | 정지(착지 경직) |

- 포물선은 Drop·JumpUp에만 적용, **Boost는 직선**.
- 공중 중 `e.pos`를 직접 세팅(충돌 무시), 착지점에 정확히 꽂힘.

### 1.3 현재 방식의 문제 (개편 사유)

1. **평상시에 몹별 게이팅이 불가능** — `NavMeshPathfinder`가 `agentMask`를 무시.
2. **물리감 없음** — 선형 보간 + **대칭 사인**. 가속 낙하가 없다.
3. **낙차와 무관하게 공중시간 고정(30틱)**.
4. **층 전환 지점을 저작자가 통제 못 함** — 기하 자동판정이라 "여기서 뛰어내려라"를 못 지정.
5. **평상시 ↔ 예측 구조 불일치** — "예측은 되는데 실제는 다르게" 류 괴리 위험.

## 2. 개편 요구사항 (KJH)

- 맵에 **손으로 마커를 배치**해 층이동 지점을 지정. **배치가 쉬워야 한다**(최우선).
- 마커마다 방향·허용 몹을 지정.
- 규칙: **하강은 누구나** / **작은 상승은 지상몹 전부** / **큰 상승은 Traversal만** / 공중몹은 마커 불필요.
- 현재 **포물선·낙하 속도 방식 전면 교체**.
- **주저·멈칫이 경로 길이에 비례**. 단, 작은 단차도 0은 아님.
- **구조물을 절대 뚫지 않아야 함.**
- **포물선을 눈으로 보고, 자동 산출된 뒤 직접 튜닝**할 수 있어야 함.
- **퀄리티가 최우선.**
- 기존 구조에 얽매이지 않는다.

## 3. 확정된 결정

### 3.1 마커 종류 = **드롭다운 3종**
체크박스 마스크 대신 **종류 하나 고르기**로 저작한다(배치 쉬움 우선).

| 종류 | 하강 | 상승 |
|---|---|---|
| **① 일반** | 전 지상몹 | 전 지상몹 |
| **② 상승제한** | 전 지상몹 | **Traversal 특성만** |
| **③ 하강전용** | 전 지상몹 | **불가(아무도)** |

③은 고낙차 절벽용 — 떨어질 순 있지만 Traversal조차 못 올라오는 곳.
(예외가 생기면 나중에 "커스텀" 항목을 추가한다.)

### 3.2 역할 분담 — NavMesh vs 마커
- **NavMesh = 연속으로 걸을 수 있는 표면 전부.** 평지 + **경사로**(최대 경사각 이내) + 작은 단차(step height 이내). 램프로 층을 오르내리는 건 **그냥 Walk**이고 게이팅 대상이 아니다.
- **마커 = 불연속 전환만.** 절벽·틈·step height를 넘는 단차·도약. **게이팅은 여기에만.**

### 3.3 게이트는 **진행 방향**에 걸린다
내려갈 땐 누구나, 올라갈 땐 제한. 따라서 마커 하나는 **방향이 다른 링크**로 구워지고
각자 권한을 가진다(③은 상승 링크를 굽지 않음).

### 3.4 표시·길이 = **직선**
- **표시**: 출발→착지 **직선**. 배치·읽기가 단순.
- **길이**: 그 **직선 거리**. 주저·멈칫 비례의 기준.
- **실제 이동은 직선이 아니라 포물선**(3.5). 저작 표현과 실제 궤적을 분리한다.

### 3.5 이동 모델 = **정점 보장 탄도(ballistic)**
선형 보간·대칭 사인·고정 틱을 폐기하고 **중력 적분**으로 교체.

1. 궤적의 **정점(apex)** = `max(출발.y, 착지.y) + clearance`.
2. 그 정점에 닿는 **수직 발사 속도**를 역산.
3. **중력으로 매 틱 적분** → 착지까지의 **비행 시간이 물리로 결정**(고정 틱 폐기).
4. 수평 속도 = 수평거리 ÷ 비행 시간.

효과:
- **점프 느낌 보장** — 항상 확실히 솟는다. **하강도 먼저 위로 솟았다 떨어진다**(가장자리에서 흘러내리지 않고 박차고 뛰어내림).
- **낙하는 중력으로 가속** → 비대칭, 쿵 떨어짐. 낙차 클수록 공중시간 길어짐.

### 3.6 clearance = **길이 비례 희망값 → 충돌 검증으로 자동 하향**
구조물 뚫림을 원천 차단한다. clearance는 최종값이 아니라 **희망값**이며,
**실제 값 = min(희망값, 공간이 허용하는 값)**.

**저작/베이크 시점 검증 절차**
1. **궤적 스윕** — 계산된 포물선을 따라 **몹 캡슐을 쓸어** 정적 지오메트리와 충돌 검사. 정점뿐 아니라 **경로 전체**(중간 기둥 포함).
2. **자동 맞춤** — 충돌하면 clearance를 **뚫리지 않는 최대치까지 자동 하향**.
3. **불가 판정** — 최소 높이로도 뚫리면 마커를 **무효(빨강)** 로 표시. 저작자가 위치/종류를 고쳐야 함.
4. **결과를 링크에 구움** — 검증된 발사 파라미터만 저장.

### 3.7 검증 기준 = **허용 몹 중 가장 큰 캡슐**
몹마다 캡슐이 다르다(대형 3배, 돌진몹 반경 1.5배). 링크에 허용된 몹 중
**최대 크기**로 검증한다. 안 그러면 "그런트는 통과하는데 대형몹은 박히는" 상황이 난다.
종류(3.1)가 허용 몹을 정하므로 최대 크기는 자동으로 정해진다.

### 3.8 주저·멈칫 = **직선 길이 비례**
- **기준**: 링크의 **직선 길이** 하나로 주저·멈칫 **둘 다** 산출.
- **데드존 없음** — 작은 단차도 **0이 아닌 최소값**. 짧아도 살짝 주저하고 살짝 멈칫한다.
- **가속형 곡선** — 짧을 땐 완만, 길어질수록 급격히 증가.
  `틱 = 최소틱 + 곡선(길이) × 계수`, **상한 클램프**.
- 곡선은 **AnimationCurve**로 노출(주저용·멈칫용 각각) → 눈으로 모양 조절.
- **마커별 오버라이드** 가능.

> 감수한 단순화: 수평으로 긴 도약과 낙차 큰 낙하가 길이가 같으면 같은 값을 받는다.
> 어색한 지점은 해당 마커만 오버라이드로 잡는다.

### 3.9 저작 UX — **자동 산출 → 눈으로 확인 → 손으로 튜닝**

**배치**
- **2클릭 생성 툴**: 출발 클릭 → 착지 클릭 → 마커 완성.
- **끝점 드래그 핸들**: Scene 뷰에서 양 끝을 직접 집어 옮김.
- **바닥 자동 스냅**: 끝점을 놓으면 아래 표면에 붙음 → Y를 안 만져도 됨.
- **종류 드롭다운**(3.1) 하나로 권한 지정.

**확인 (실시간)**
- **궤적 실시간 표시** — 드래그하는 동안 실제 날아갈 포물선이 그려짐.
- **충돌 색상** — 안전하면 **초록**, 뚫리면 **빨강 + 충돌 지점 표시**.
- **캡슐 실루엣** — 궤적 위 일정 간격으로 그려 천장과의 여유를 눈으로 확인.
- **고스트 재생 미리보기** — Play 없이 에디터에서 몹 고스트가 궤적을 **실제 속도로** 날아감.
  주저·비행·멈칫 타이밍까지 확인 가능(느낌 튜닝의 핵심).

**튜닝 (손잡이 2개)**

| 손잡이 | 조작 | 효과 |
|---|---|---|
| **정점 높이(apex)** | 궤적 꼭대기를 잡고 **위아래 드래그** | 얼마나 크게 솟는가 |
| **중력** | 슬라이더 | 스냅하게 떨어지나, 붕 뜨나 |

나머지(비행 시간·수평 속도·정점 위치)는 이 둘에서 자동으로 따라온다.

**자동/수동 상태**
- 기본은 **자동**. 손대면 **수동(override)** 으로 전환.
- **"자동으로 되돌리기" 버튼**으로 언제든 복귀.
- 수동 튜닝 중에도 **충돌 검사가 계속 돌아** 구조물로 끌면 즉시 빨강 → 모르고 망칠 수 없음.

### 3.10 **평상시 라우팅 = 옵션 A** (NavMesh + NavMeshLink + Area)

**퀄리티 최우선 기준으로 채택.** NavMesh가 도약 링크까지 **비용에 포함해 전역 최적 경로**를
한 번에 계산하므로, "돌아갈까 / 뛰어내릴까"를 전체 경로 길이로 올바르게 판단한다.
(계층 근사인 영역 그래프 방식은 가까운 마커를 두고 먼 마커를 고르는 실수가 구조적으로 생김.)

**Bake: 마커 → NavMeshLink + 그래프 링크**

| 마커 종류 | 굽는 NavMeshLink |
|---|---|
| ① 일반 | 양방향 1개, Area = `Leap` |
| ② 상승제한 | **단방향 2개** — 하강: Area `Leap` / 상승: Area `LeapTraversal` |
| ③ 하강전용 | **단방향 1개**(하강만), Area = `Leap` |

②는 한 링크에 방향별 권한을 못 주므로 **단방향 2개**로 굽는다 → 3.3이 그대로 표현된다.

**런타임 게이팅 = 몹별 areaMask**
- 지상 일반몹: `areaMask = 기본 + Leap` (LeapTraversal 제외) → NavMesh가 **알아서 우회**.
- Traversal몹: `areaMask = 기본 + Leap + LeapTraversal`.

경로 계산 단계에서 못 쓰는 링크가 **원천 배제**되므로 실행 중 재검사가 필요 없다.
→ **1.3-①(평상시 게이팅 불가) 해결.**

**마커 진입 판정**: `NavMeshAgent`를 쓰지 않고 코너를 직접 따라가므로,
**다음 코너가 어떤 마커의 출발점과 (오차 내) 일치하면** 그 마커의 링크로 판정하고
구워둔 탄도 파라미터로 traversal을 시작한다. 마커 수가 적고 좌표가 고정이라 비용·정확도 문제 없음.
**→ §4에서 실측으로 검증 완료.**

### 3.11 **링크 비용 보정 — 필수 항목**
도약은 **주저 + 비행 + 착지 경직** 때문에 실제로는 기하 거리보다 훨씬 오래 걸린다.
보정하지 않으면 몹이 조금만 이득이면 아무 데서나 뛰어내려 **경직으로 굳는** 모습이 잦아져
**오히려 품질이 떨어진다.**

```
소요틱   = 주저틱 + 비행틱 + 멈칫틱
환산거리 = 소요틱 × TickDelta × EnemyMoveSpeed
링크비용 = 환산거리        // NavMeshLink 비용으로 지정
```

이러면 NavMesh가 "걸어서 N미터 우회" vs "도약 = 환산거리 M미터"를 **공정하게 비교**한다.
→ 몹은 **정말 이득일 때만 뛰어내리고**, 아니면 돌아간다.

### 3.12 **링크 비용은 예측 그래프에도 동일 적용**
현재 그래프 간선 비용은 **순수 직선거리**다([GraphPathfinder.cs:52](../../PrecogPrototype/Assets/_Project/Bridge/GraphPathfinder.cs)):
```csharp
int cost = Mathf.Max(1, Mathf.RoundToInt(Vector3.Distance(...) * 100f));
```
→ 도약의 주저·비행·멈칫이 **전혀 반영 안 됨**. 그래서 NavMesh만 보정하면 두 시스템이 **정반대 판단**을 한다.

| | 도약 비용 | 경사로 우회 | 선택 |
|---|---|---|---|
| 평상시(NavMesh, 보정 후) | 환산 7.2m | 6m | **경사로** |
| 예측(그래프, 미보정) | 직선 3m | 6m | **도약** |

→ 예측 화면은 "몹이 뛰어내려 덮친다"인데 실제로는 경사로로 돌아온다. **플레이어가 예측을 보고 수를 짜는 게임에서 치명적**이다.

**그래서 그래프 간선 비용도 같은 환산거리를 쓴다:**
```
걷기 링크 : cost = 직선거리 × 100                        (현행 유지)
도약 링크 : cost = (소요틱 × TickDelta × 이동속도) × 100   ← 환산거리
```
정적 값이라 Floyd-Warshall 사전계산은 그대로 유효하다.

> 남는 차이: NavMesh는 연속(코너 깎기)이라 절대 경로 길이는 여전히 다르다.
> 다만 **"도약이냐 걷기냐"의 저울은 일치**하게 되며, 그게 핵심이다.

### 3.13 층이동 혼잡 대책 = **착지 슬롯 + 정원·대기 + 국소 대체**

여러 몹이 동시에 같은 링크로 뛰어들면 **같은 착지점에 무더기로 겹친다**(비행 중엔 분리 스티어링도 안 먹음).

1. **착지 슬롯** — 착지점 둘레 링에 슬롯 N개. 도약 시 하나를 점유해 그곳으로 착지.
   슬롯은 **자동 생성 + 베이크 시 검증**(바닥·충돌), 못 쓰는 건 자동 폐기.
   에디터에서 **유효=초록 / 폐기=빨강**으로 표시되고, 개수·퍼짐 반경을 드래그로 튜닝 + 자동 복귀 가능.
   간격은 **허용 몹 중 최대 반경 × 2 이상**이 되도록 자동 산출.
   (`ArenaNavLink.landingSlotCount` / `landingSpread` 필드가 이미 있으나 **미사용** — 이걸 살린다.)
2. **정원 + 순번 대기** — 동시 비행 가능 수를 제한, 초과 시 발판에서 대기.
   순서는 `entityId` 오름차순 등 **결정론적 동률 해소**.
3. **국소 대체** — 발판에 도착했는데 링크가 꽉 찼으면, **근처에 같은 목적지로 가는 다른 링크가 비었는지만** 확인하고 그쪽으로.

> **③은 "전역 동적 비용"이 아니다.** 혼잡에 따라 링크 비용을 매 틱 바꾸면
> 그래프의 **Floyd-Warshall 사전계산 표를 매번 다시 만들어야 해서**(O(V³)) 예측에서 불가능하다.
> 그래서 전역 재라우팅 대신 **국소 판단**으로 한정한다.

**구현 부담이 낮은 이유**: 점유 상태를 위한 **별도 자료구조가 필요 없다.**
적이 이미 `activeTraversalLinkId`를 들고 있으므로, **슬롯 번호 1바이트만 추가**하면
"링크 X의 슬롯 Y가 비었나 / 정원이 찼나"는 **적 배열을 훑어** 판정된다.
적 상태는 포크 시 복사되므로 **예측 결정론도 자동**.

### 3.14 몹 거동 — 개체 개성값 · 공중 추적

**개체별 고정 개성값** (ADR-0004 개정으로 허용, 2026-07-20)
- 지금은 모든 몹이 **동일한 분리 가중치**를 써서, 정면으로 마주치면 밀어내는 힘이 대칭이 되어
  **거울처럼 진동**하고 무리가 한 덩어리로 움직인다.
- → **분리 세기 배율**(최대치 대비 낮추는 곱)을 **개체별 고정 상수**로 준다.
- 요구조건: 스폰 시 1회 결정·이후 불변, `EnemySim`에 저장, **`WorldHash`에 포함**,
  산출은 결정론적(`Hash(worldSeed, enemyId)` 권장).
- 확장 여지: 포위 각도 오프셋, 리패스·쿨타임 위상차.

**공중 추적 = `lastGroundedPos`**
- 현재 버그: 플레이어가 공중에 뜨면 `NavMesh.SamplePosition`(반경 4m)이 실패 →
  `MoveKind.None` → [EnemyMovement.cs:25](../../PrecogPrototype/Assets/_Project/Sim/Enemies/EnemyMovement.cs)에서 **몹이 완전 정지**.
  반면 그래프의 `NearestNode`는 반경 제한이 없어 **예측에선 계속 추적** → 심각한 괴리.
- → `PlayerSim`에 **`lastGroundedPos`** 추가(접지 시 갱신). 추적 목표는
  **접지 중이면 현재 위치, 공중이면 `lastGroundedPos`**. 스폰 시 초기값 = 스폰 위치.
- **`WorldHash`에 포함 필수.**
- 지면 투영(레이캐스트) 대신 이 방식을 택한 이유: **질의 비용 0**이라 337k 포크에 유리.
- 감수: 멀리 점프하면 몹이 잠깐 **출발 지점으로** 달림(착지 즉시 재조준).

**`MoveKind.None` 안전망 — 넣지 않음(보류)**
경로 실패 시 플레이어 수평 방향으로 걷게 하면 **낙사를 유발**할 수 있다. 나중에 재검토.

### 3.15 검증은 저작 시점, 런타임은 **재생만**
검증·자동맞춤은 전부 에디터/베이크에서 끝낸다. 런타임은 **구워진 궤적을 재생만** 한다.
→ 런타임 충돌검사 **0회**, 예측 337k 포크에도 부담 없음, **결정론 유지**.

### 3.16 폐기 대상
- 대칭 사인 포물선, 고정 공중시간(30틱), 관련 상수.
- `NavMeshPathfinder`의 낙차 기하 자동판정(`DropDetect*`) — 층 전환은 전부 명시 마커로.

### 3.17 범위 밖(이번엔 안 함)
- **공중몹 항법 분리**(마커 무시하고 3D 자유비행/호버) — 나중에 별도로 다룬다.
- **예측용 그래프 밀도 개선** — 아래 참조.

> **알려진 잔여 격차(수용)**: 평상시는 NavMesh(연속·최적), 예측은 성긴 그래프를 쓰므로
> **어느 길로 갈지**가 다를 수 있다. NavMesh는 결정론 포크가 불가하므로 하이브리드 구조상
> 불가피하다. 다만 확정 경로를 실제 재생하는 **Following은 그래프로 돌리므로
> "예측한 대로 움직이는 것"은 보장**된다. 예측 경로 품질을 더 올리려면
> **그래프를 더 촘촘하게 만드는 별개 작업**이 필요하며, 이번 범위 밖이다.

## 4. 실측 결과 (2026-07-20, Arena_3 · 런타임 NavMesh)

### 4.1 NavMeshLink가 런타임 NavMesh에 연결되는가 → **연결됨**
서로 걸어서 못 가는 두 지점(양방향 `PathPartial`)에 `NavMeshLink`를 런타임 생성하니
**`PathComplete`로 바뀌었다.** 옵션 A의 전제가 검증됐다.

- 대상: `A=(-44.889, 0.083, -44.889)` ↔ `B=(-6.444, 3.667, -12.667)`
- NavMeshSurface `agentTypeID=0`, agent radius 0.5 / height 2 / climb 0.75 / slope 45.
- **주의**: 런타임 생성 직후 **같은 프레임에는 반영되지 않는다.** 다음 프레임부터 경로에 잡힌다.
  → Bake 시점에 만들고 한 프레임 뒤부터 유효하다고 봐야 한다.

### 4.2 링크가 `corners`에 어떻게 나오는가 → **끝점 2개가 연속 코너로**
```
[0] (-44.889, 0.083, -44.889)   ← 출발점(= 링크 시작점)
[1] (-44.889, 0.083, -44.889)   ← 링크 시작점 (중복)
[2] ( -6.444, 3.667, -12.667)   ← 링크 끝점
[3] ( -6.444, 4.195, -12.667)   ← 최종 목표(표면 스냅)
```
- 링크 구간은 **`링크 시작점 → 링크 끝점`이 연속 코너 쌍**으로 나타난다.
- **출발점과 링크 시작점이 겹치면 같은 좌표 코너가 중복**된다 → 진입 판정 시 **연속 중복 코너를 병합**해야 한다.
- **메타데이터는 없다.** `NavMeshPath`의 공개 API는 `corners`와 `status`뿐이라
  "이 구간이 링크였다"를 알려주는 정보가 **원천적으로 없다**
  (링크 정보를 주는 `NavMeshAgent.currentOffMeshLinkData`는 에이전트를 써야 하는데 우리는 안 씀).
  → **좌표 매칭이 유일한 방법**이며, 3.10의 설계가 그대로 유효하다.

### 4.3 구현 시 주의 (측정 중 발견)
`NavMesh.CalculatePath`의 **시작점을 삼각분할 정점(폴리곤 모서리)에 두면 질의가 실패**할 수 있다
(방향에 따라 `PathPartial`이 되는 비대칭 현상). 몹 위치는 보통 면 내부라 문제없지만,
**경로 질의 전 `SamplePosition`으로 면 위로 당기는 처리**를 유지해야 한다.

## 5. 상세 설계

### 5.1 마커 컴포넌트 (`TraversalLink`)
- **끝점 2개**(takeoff / landing) — Scene 뷰 드래그, 바닥 스냅.
- **종류**: 일반 / 상승제한 / 하강전용 (→ 방향별 권한·Area 결정).
- **궤적**: `clearance`(자동/수동 + 값), `중력`.
- **주저·멈칫**: 곡선에서 자동 산출 + 개별 오버라이드.
- **검증 결과**: 유효/무효, 자동 하향된 실제 clearance.

### 5.2 탄도 수식
`P0`=출발, `P1`=착지, `g`=중력, `apexY = max(P0.y, P1.y) + clearance`

```
vy0     = sqrt(2 · g · (apexY − P0.y))      // 정점까지 오를 수직 속도
t_up    = vy0 / g
t_down  = sqrt(2 · (apexY − P1.y) / g)
T       = t_up + t_down                      // 총 비행 시간(물리로 결정)
v_horiz = (P1 − P0)의 수평성분 / T
```
매 틱 고정 `dt`(`SimConfig.TickDelta`)로 적분. 높이차가 있으면 `t_up ≠ t_down` →
**자연스러운 비대칭**(빠른 낙하)이 공짜로 나온다.

### 5.3 Bake
마커 1개 →
- **NavMeshLink**(종류별 1~2개, Area·단방향·**비용 보정**) — 평상시용
- **그래프 링크**(1~2개, `agentMask`) — 예측용

양쪽 모두 **검증된 발사 파라미터**(vy0, v_horiz, g, 주저·멈칫 틱)를 공유 →
**동일 궤적**을 재생.

### 5.4 런타임 실행
`발판까지 걷기 → 주저(길이비례) → 탄도 비행(중력 적분) → 착지 경직(길이비례)`.
현재 `StepTraversal`의 선형+사인 구간을 탄도 적분으로 교체.
못 쓰는 링크는 **길찾기 단계에서 이미 배제**되므로 실행 중 재검사 불필요.

### 5.5 결정론
- 탄도 적분은 **고정 dt** 기반 → 예측 포크에서 동일 재현.
- 주저·멈칫 틱도 구워진 값 → 재현 보장.
- 예측 루프에서 NavMesh 호출 없음(계약 §8.3 유지).
- 궤적 검증은 저작 시점에만 → 런타임 물리질의 0.

### 5.6 부수 효과 (의도된 것)
큰 도약일수록 착지 경직이 길어져 **플레이어에게 열리는 딜각**이 된다.
몹이 크게 뛰면 그만큼 위험을 지는 구조 → 전투에 리스크/리워드가 생긴다.
