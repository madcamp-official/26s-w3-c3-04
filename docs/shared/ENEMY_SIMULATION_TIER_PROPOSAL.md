## 1. 요약

`OPTIMIZATION.md`가 이미 설계해둔 `EnemySimulationTier`(Precise/Coarse/Dormant)가 아직 구현 안 됐는데,
지금 게임 설정(`SimConfig.SpawnCap = 40`, 최대 동시 적 40마리)이 이미 예측 시스템의 성능 한계를
넘어서는 규모를 요구하고 있어서 우선순위를 올려야 한다. 실측 수치와, 설계 검토 중 발견한
"Tier만으론 안 풀리는" 두 가지 구멍을 정리했다.

## 2. 실측: 적 수별 Beam Search 비용

`Precog → 예측 성능 벤치마크 (적 수별)` 메뉴로 직접 재현 가능(스텁 충돌·경로찾기 기준 —
실제 `Physics.CapsuleCast`/NavMesh 비용은 **포함 안 됨**, 즉 아래 숫자는 최선의 경우다).

설정: Full(Beam 12 / 3초 / 180틱), 순수 Beam Search 알고리즘 비용만 측정.

| 적 수 | 실측 시간 | 목표(200ms) | 하드리밋(300ms) |
| ---: | ---: | :---: | :---: |
| 8  | 74.19ms   | 통과 | 통과 |
| 16 | 179.38ms  | 통과(빠듯) | 통과 |
| 32 | 583.22ms  | **초과** | **초과 (1.9배)** |
| 50 | 1267.70ms | **초과** | **초과 (4.2배)** |
| 64 | 2017.31ms | **초과** | **초과 (6.7배)** |

증가 패턴이 `SimStep.Separate`의 적 쌍 분리 수(O(N²))와 정확히 일치한다:

```text
적 8   → 28쌍     (OPTIMIZATION.md 1장 예측치와 일치)
적 16  → 120쌍
적 32  → 496쌍
적 50  → 1,225쌍
적 64  → 2,016쌍
```

시간/쌍수 비율이 적 수가 늘수록 1.0에 수렴한다(8마리: 2.65 → 64마리: 1.0006) — 즉 낮은 적
수에서는 고정 오버헤드가 섞여 있지만, 높은 적 수에서는 **분리 비용이 거의 전부**를 차지한다.

## 3. 왜 지금인가

`Sim/Core/SimConfig.cs`:

```csharp
public const int SpawnIntervalTicks = 45;   // 0.75초마다 한 마리
public const int SpawnCap           = 40;   // 최대 동시 적 수
```

**실제 게임이 이미 최대 40마리 동시 존재를 목표로 설정돼 있다.** 32마리(583ms)와 50마리(1268ms)
사이 어딘가인 40마리는 하드리밋을 3배 안팎으로 넘길 것으로 추정된다. "나중에 몹이 많아지면
할 최적화"가 아니라 **현재 스펙에서 이미 막히는 문제**다.

### 품질 축소만으로는 부족함

`OPTIMIZATION.md` 12장의 동적 품질 축소(Beam 12→6, 3초→2초 등)를 전부 적용해도 최대 3배
정도 절감이 한계다(2017ms → 약 670ms). 64마리를 200ms 안에 넣으려면 약 10배 절감이
필요한데, 이 정도면 Beam·깊이를 이미 만들어둔 "Mini"(빠른 반응용, 0.75초/행동 4개) 수준까지
깎아야 해서 "3초 본탐색"이라는 목적 자체가 사라진다. **구조적 개선(Tier) 없이는 안 된다.**

## 4. 제안: EnemySimulationTier (OPTIMIZATION.md 3장 그대로)

```csharp
public enum EnemySimulationTier : byte { Precise, Coarse, Dormant }
```

- **Precise**(상한 8~12마리): 정확한 공격·이동·LOS·충돌·분리·런지 타깃 평가. 대상 = 공격 중,
  공격 범위 근처, 예측 시간 안에 플레이어를 공격 가능, 런지 후보 가능, 경로가 플레이어 예상
  이동과 겹침.
- **Coarse**: 정적 Navigation Graph로 이동은 계속하되(정지 아님) 정밀 물리·LOS 생략. 위험권
  진입 시 Precise 승격.
- **Dormant**: 최소 타이머만 진행. 영향 가능해지면 Coarse 승격.
- 재분류 주기: 6~15틱마다(매 틱 아님).

예상 효과(추정치, 실측 아님): Precise가 8~12로 고정되면 비싼 부분이 적 총수와 무관해지므로,
40~64마리에서도 3초 기준 100~200ms대로 수렴할 것으로 본다. 5초로 늘리면 틱 수가 1.67배
늘어나는 만큼 비례 증가(약 170~220ms 추정) — 이것도 실제로 만들어서 벤치마크 도구로
재확인해야 확정할 수 있다.

## 5. 설계 검토 중 발견한 두 가지 구멍

Tier를 문서 그대로 넣으면 놓치는 부분이 있어서, 구현 전에 같이 결정하고 싶다.

### 5.1 Precise 캡(8~12)과 "공격 중인 적은 제외 안 함" 규칙의 충돌

`OPTIMIZATION.md` 12장은 "이미 공격 Windup/Active인 적은 Precise에서 제외하지 않는다"고
못박아뒀는데, 동시에 Precise 상한을 8~12로도 못박아뒀다. **동시에 공격 중인 적이 12마리를
넘으면 이 두 규칙이 정면으로 충돌한다.**

문서 5장 "동시 공격 슬롯"(동시 공격 허용 최대 4~6마리)이 이걸 풀어주는 장치인데 — **이
슬롯 시스템 자체가 아직 `EnemyBrain.Step`에 없다.** 지금은 각 적이 자기 쿨타임·거리만 보고
독립적으로 Windup에 들어가서, 몹 다수가 동시에 사거리에 들어오면 전부 동시에 공격을 시작할
수 있다. **Tier만 넣고 동시공격슬롯을 안 넣으면, 다수 적이 한꺼번에 몰리는 "진짜 위험한"
순간에 오히려 Precise 캡을 넘겨서 일부 공격 중인 적이 부정확하게 시뮬레이션될 위험이 있다.**

→ **제안**: Tier와 동시공격슬롯(4~6)을 세트로 같이 구현. 슬롯이 실제 게임의 동시 공격
가능 수 자체를 4~6으로 제한해주면, Precise 8~12 안에서 "공격 중 적(최대 4~6) + 접근 중
위협(나머지 슬롯)"이 항상 여유 있게 들어간다.

### 5.2 원거리 솔저는 거리 기준 분류가 안 맞음

Precise 분류가 "플레이어와의 거리"만 본다면, 원거리 솔저(교전 사거리 `RangedBandMax`≈16m +
투사체 비행 거리)가 근접몹(사거리 ~1.4m) 기준의 "가깝다"를 통과 못 해서 Coarse/Dormant로
밀려날 수 있다. 그러면 **투사체 자체가 생성이 안 돼서**, 이번에 예측 쪽에 새로 넣은
`FutureThreatObserver`(투사체 명중 예측, `ThreatEvaluator.cs`)가 평가할 대상 자체가 사라진다.

→ **제안**: 분류 기준의 "공격 범위 근처"·"영향 가능 범위"(`OPTIMIZATION.md` 4장 공식)를
아키타입별 실제 교전 사거리로 계산. 고정 거리 임계값 하나로 퉁치지 말 것.

2. `Sim/Core/EnemySim.cs`(tier 필드), `Sim/AI/EnemyAI.cs`(EnemyBrain 분기), `Sim/Enemies/EnemyMovement.cs`,

3. 완료 후 `Precog → 예측 성능 벤치마크 (적 수별)`로 8~64마리 재측정해서 이 문서 수치와 비교
