# 팀원 문서 v1.1 검토 — 우리 계획과의 차이

> 대상: "미래 잔상 예측 액션 — 3인 개발 통합 계획서 · 규칙 기반 결정론적 적 AI 보강판 (v1.1)"
> 기준: [GDD.md](GDD.md)

---

## 1. 막기가 통째로 없습니다 — 제일 큽니다

`ControlFrame`에 `dashPressed / jumpPressed / attackPressed / wallRunPressed`만 있고 **블록 입력이 없습니다.** `PlayerSimState`에 가드 게이지도 없습니다. 문서 어디에도 막기가 등장하지 않습니다.

이게 세 군데를 동시에 무너뜨립니다.

**첫째, 칼만 든 플레이어가 원거리 적에 대응할 방법이 사라집니다.** 문서는 원거리 적을 확정 스코프에 넣어놨는데(2.1), 총이 없고 막기도 없으면 투사체에 답이 없습니다. 접근하는 동안 일방적으로 맞습니다.

**둘째, 우리 예지 설계의 핵심이 날아갑니다.** 막기를 탐색에 넣으면 *"모든 투사체를 지오메트리로 피하는 경로를 찾아라"*(어려움)가 *"경로는 아무거나 잡고 날아오는 건 막아라"*(쉬움)로 바뀝니다. 막기가 없으면 8장의 Beam Search는 **회피 경로만 찾아야 하고, 난전에서 그런 경로는 대체로 존재하지 않습니다.** 18.1의 "탐색 생존 후보 없음"이 예외가 아니라 기본값이 될 위험이 있습니다.

**셋째, 경로 카드의 비용 축이 하나 사라집니다.** "4킬인데 가드를 다 태움" 같은 선택지가 성립하지 않습니다.

---

## 2. 재생 방식이 다릅니다 — 스플라인이 아니라 입력 재생

이게 두 번째로 큽니다. 우리는 **재생 중 이동을 스플라인으로 고정**하기로 했습니다. 문서 10.1은 다릅니다.

```csharp
ControlFrame control = selectedPath.controlFrames[replayTick];
SimulationKernel.SimulateTick(ref runtimeWorld, control);
```

**저장된 입력을 다시 시뮬레이션에 먹여서 위치를 만들어냅니다.** 위치를 정해주는 게 아닙니다.

여기서 **플레이어 결정론이 필수가 됩니다.** 그래서 문서가 `PlayerSimState`를 22개 필드짜리 구조체로 만들고, 이동·대시·점프·벽타기를 전부 정수 틱으로 강제하고, 디싱크 검사에 "플레이어 위치 2cm 이하"를 넣은 겁니다. 스플라인이면 이 전부가 필요 없습니다 — 위치가 그냥 정해져 있으니까요.

**어느 쪽이 맞다고 단정하진 않겠습니다.**

| | 스플라인 (우리) | 입력 재생 (문서) |
| --- | --- | --- |
| 플레이어 결정론 | 불필요 | **필수** |
| 컨트롤러 손맛 튜닝 | 자유 | 정수 틱에 묶임 |
| 디싱크 위험 | 적 AI만 | 플레이어까지 |
| Miss 시 복귀 | 스플라인 위 위치 | 자연스러움 |
| 구현 난이도 | 낮음 | 높음 |

문서 방식이 더 "진짜"이고 Miss 복귀가 자연스럽습니다. 대신 **1주일에 부동소수점 누적 오차까지 잡아야 합니다.** 벽타기와 대시가 얽힌 상태에서 60틱 뒤 위치를 2cm 안에 맞추는 건 만만치 않습니다.

**그리고 이게 컨트롤러 손맛을 직접 제약합니다.** 우리는 "칼 무쌍의 재미는 손맛에서 나온다"를 전제로 컨트롤러를 자유롭게 두기로 했는데, 문서대로면 그 자유가 없습니다.

## 3. 단타 / 홀드 분화가 없습니다

문서의 예지는 하나뿐이고, 항상 후보 3개를 제시합니다. 우리가 정한 것과 다릅니다.

| | 우리 계획 | 문서 |
| --- | --- | --- |
| 특정 몹 조준 + 단타 | 그 몹만 안전하게 죽이는 루트, **게이지 저소모** | 없음 |
| 홀드 | 다수 학살 루트, 고소모 | 이것만 있음 |

이게 문서 16.4의 성능 문제와 직결됩니다. 5초/Beam 36에 **300ms**를 목표로 잡아놨는데, 화면 멈춘 채 0.3초 대기입니다. 단타는 목표가 고정이라 탐색이 1마리짜리고 훨씬 쌉니다 — **급할 때 즉시 나오는 응급 옵션**이 통째로 빠졌습니다.

## 4. 적에게 `health`가 있습니다 — 한방컷이 아닙니다

```csharp
public struct EnemySimState
{
    public int health;   // ← 이게 있으면 안 됩니다
}
```

우리 GDD에 이렇게 못박아뒀습니다 — **"적이 두 방 이상 걸리는 순간 경로 시뮬레이션이 훨씬 복잡해진다. 이건 밸런싱 여지가 아니라 구조적 제약이다."**

재훈 님이 HP를 낮게 잡은 이유가 바로 예측 시스템을 쉽게 만들기 위해서였습니다. `health`가 들어가면 Beam Search가 "이 경로로 몇 대 때리나"까지 추적해야 하고, 이진 판정(죽는다/안 죽는다)이 깨집니다.

`health = 1`로 쓸 거면 필드 자체를 빼는 게 맞습니다. 필드가 있으면 누군가 반드시 2를 넣습니다.

---

## 5. 손맛 검증 시점이 없습니다

우리가 정한 순서는 **칼 무쌍 → 웨이브 → 예지**였습니다. 이유도 명확했습니다 — 칼 무쌍이 재밌고 난전이 실제로 패닉을 만들어야 예지가 가치를 갖고, 예지를 먼저 만들면 예측할 대상이 없어 허공에 짓게 됩니다.

문서 14장은 **Day 1부터 세 명이 병렬**로 갑니다. C는 Day 1에 Beam Search 골격, Day 2에 이미 "경로 생성 + 실제 재생" 통합이 목표입니다.

**"타격감"이라는 단어가 문서에 처음 나오는 게 Day 5입니다.** 5일차에 "칼 휘두르는 게 재미없다"를 발견하면 되돌릴 시간이 없습니다. **이게 이 문서에서 제가 제일 걱정하는 부분입니다.**

## 나머지 차이 (영향 순)

| 항목 | 우리 계획 | 문서 |
| --- | --- | --- |
| **중형몹 + 마무리 컷신** | 있음 (컷신 중 무적) | **없음.** 적 2종만 |
| **아이템** | 회복·방어막 맵 배치 + 처치 드랍 | **없음** |
| **도망 경로** | 답 없으면 도망 경로 제시 | **없음.** "생존 경로 없음" 표시하고 끝 |
| **경로 카드** | 킬 수 / 난이도 / **피격 수** / **가드 소모** / 시간 | 안전·제거·스타일 **점수**. 피격 수와 가드 소모 없음 |
| **게이지 수치** | 폐기 (미정) | **20 단위, 1~5초 부활** |
| **더블점프** | 확정 | 명시 없음 (`jumpCount` 필드만 존재) |
| **아레나** | 3개 + 길목 | 1개 (프로토타입이면 타당) |
| **역할** | 올라운더 3인, 시스템별 1차 담당 | **게임 1명 / 시뮬레이터 2명** 전문화 |
| **일반 공격 위치 보정 + 짧은 무적** | 확정 | 없음 |

역할 분담은 짚어둘 만합니다. **A 혼자 런타임·맵·NavNode 배치·적 표현·웨이브·잔상 프리팹·어댑터를 전부 합니다.** B와 C 둘이 시뮬레이터를 나눠 갖는데, A가 병목이 되면 B/C가 검증할 게임이 없습니다. 그리고 GDD에는 "올라운더 3인, 역할 고정 없음"으로 적혀 있습니다.

## 문서가 우리보다 나은 부분 — 이건 가져와야 합니다

깎을 생각으로만 읽으면 손해입니다. 실제로 더 나아간 게 있습니다.

- **난수를 아예 제거한 것.** 우리 GDD는 "시드 고정 후 미리 굴려 큐에 저장"이었는데, 문서는 난수 자체를 없애고 우선순위 트리로 갑니다. **더 강한 결정론이고 디버깅이 훨씬 쉽습니다.** (부작용: 적이 완전히 예측 가능해져 패턴이 단조로울 수 있습니다. 관찰 필요.)
- **동률 해소 규칙을 전부 명시한 것** (7.7, 7.8). `entityId` 오름차순, `nodeId` 사전순, 겹침 시 홀짝 분리. 이게 없으면 컬렉션 순회 순서 하나로 디싱크가 납니다. 우리 GDD엔 없던 내용입니다.
- **`committedAttackDirection`.** 공격 시작 후 방향을 고정해서 무한 추적을 막습니다. 이게 있어야 예지 회피가 성립합니다. 좋은 발견입니다.
- **Drop Link 설계** (7.6). 아무 데서나 뛰어내리지 않고 맵 제작자가 심은 링크로만 하강. 우리가 논의한 것보다 구체적입니다.
- **Assembly Definition 분리와 씬 소유권 분리** (13장). 우리가 걱정한 씬 머지 충돌을 정면으로 다룹니다.
- **재생 중 `targetYaw`를 ControlFrame에 넣은 것.** 제가 지적한 "시선도 경로 데이터에 포함돼야 한다"가 반영돼 있습니다.

## 제 판단

**1번(막기)과 4번(health)은 반드시 고쳐야 합니다.** 막기는 게임 자체가 성립하지 않는 문제이고, `health`는 명시적으로 못박은 구조적 제약을 어긴 겁니다.

**2번(재생 방식)은 팀에서 결정해야 합니다.** 스플라인이냐 입력 재생이냐는 취향이 아니라 스코프를 가릅니다. 입력 재생을 고르면 플레이어 컨트롤러의 손맛 튜닝 자유가 사라지고, 1주일에 부동소수점 오차까지 잡아야 합니다. 저는 **1주일이라면 스플라인**을 권하지만, 문서 방식이 결과물로는 더 낫습니다.

**5번(순서)은 지금 고치는 게 쌉니다.** Day 1~2 어딘가에 "칼 무쌍이 재밌는가"를 확인하는 게이트를 넣으십시오. 재미없으면 전부 무의미합니다.
